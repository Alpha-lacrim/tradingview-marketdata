# Milestone 2.1 — secure same-producer session recovery

This additive protocol resolves unattended recovery after ordinary expiry. It preserves the
approved milestone-2 endpoints, renewal behavior, transactional market persistence and read
contracts. Migration 0008 is unchanged; additive 0009 supplies the recovery foundation. This
milestone installs no synchronization worker, source outbox, collector or company deployment.

## Exact request and response

POST `/api/ingest/v1/session/recover` uses the existing producer bearer authentication, HTTPS,
no-browser-Origin policy, request deadline, shared SQL quota and in-flight bound. Its body is
strict JSON, bounded to min(256 KiB, INGEST_MAX_BODY_BYTES). No compression or query credentials.
Maximum 1000 unique grants; the manifest must contain every stream currently owned by this
producer, with the previously known epochs and ownership generations. Do not omit grants to
work around a size limit or silently change them after a fence error.

```json
{
  "protocol_version": 1,
  "recovery_id": "<new durable random UUID for this operation>",
  "previous_session_id": "<last durably known session UUID>",
  "previous_session_generation": 1,
  "streams": [{
    "instrument_id": "<existing registry instrument UUID>",
    "provider": "<existing provider identity>",
    "stream": "candles",
    "source_epoch": "<unchanged durable dataset UUID>",
    "ownership_generation": 1
  }]
}
```

Placeholders must be replaced using the producer's provisioned/acknowledged identities; the
single-row example is valid only when that is its complete manifest. Admission manifests also
contain allowed_statuses: project only the five fields shown above into recovery requests.
Protocol/session/ownership versions are strict positive JSON integers bounded by BIGINT (protocol
is exactly 1). Unknown fields, duplicate stream keys and ambiguous JSON keys fail. Epochs are
checked per stream, so an already authorized multi-epoch manifest cannot be reset or merged by
recovery. The authenticated producer identity comes only from its bearer credential, never the
request body. The replacement session UUID is generated by PostgreSQL, not chosen by the client.

HTTP 200 is a typed RecoveryReceipt with protocol_version, producer_id, recovery_id,
previous_session_id/generation, new session_id, session_generation=previous+1, expires_at,
server_recovered_at, state=committed and the validated streams. The lease is 120 seconds from
the database recovery operation. Times are UTC; server_recovered_at is operational transaction
time, not an exact physical commit timestamp or a market-data source time. HTTP returns only
after the session change and acknowledgment row have committed together with synchronous_commit
on. The [OpenAPI snapshot](fastapi-v1.1-ingest-openapi.json) and RecoveryRequest/RecoveryReceipt
models define the exact typed contract; HTTP docs remain disabled and read OpenAPI is unchanged.

The request ID is producer-scoped and permanently bound to its logical request. PostgreSQL
normalizes UUIDs/integers and sorts the stream array, stores the normalized request and SHA-256,
and persists one acknowledgment. JSON whitespace/object order/stream order do not alter this
recovery identity. Batch fingerprints remain exact raw-byte hashes as in milestone 2; this is a
separate recovery contract. No X-Payload-SHA256 header is required for recovery.

## Transaction and fencing

The narrowly granted SECURITY DEFINER function ingest_recover_session(UUID,TEXT,JSONB) validates
inputs itself, locks the producer FOR UPDATE, then locks requested ownership rows FOR SHARE in
business-key order. It checks enabled/current credential key, complete ownership membership,
all requested producer/epoch/generation tuples and the expected previous session. The producer
must be expired for a new recovery. It updates only that producer's session fields and inserts
its receipt in the same transaction. The existing 0007 fence trigger remains active. Owner rows,
producer definitions, source epochs, market rows, events and upload receipts are not reassigned
or rewritten. A unique prior-session constraint complements the row lock/CAS checks.

These lock modes serialize recovery with uploads, renewal, revocation and handover; see the
[PostgreSQL 16 row-lock documentation](https://www.postgresql.org/docs/16/explicit-locking.html).
Admin changes that commit first are checked after lock acquisition. Recovery that commits first
can be invalidated by the subsequent administrator action. A successful acknowledgment never
grants immunity to later revocation. PostgreSQL still enforces every upload's current ownership
and session independently of this acknowledgment.

Two different recovery IDs expecting the same expired session have one winner. Other requests
receive a fence conflict without the winner's session UUID. Identical concurrent requests with
the same ID may all return the one saved acknowledgment. A saved recovery retry is returned
only while its replacement session is still current and the complete requested ownership still
matches. It never renews that lease, even if now expired. A later successful recovery or admin
session rotation makes the earlier receipt obsolete; ownership changes also block its replay.
A reused recovery ID with different logical contents conflicts. No endpoint lists/discovers
recovery receipts or current replacement session secrets for stale clients.

A disabled producer or revoked old key fails authentication/admission or the transaction's
recheck, including if an old server process retains its credential file. A newly rotated valid
key for the same producer can retry its known current recovery request; old keys cannot. Initial
producer/stream creation, intentional epoch changes and machine-to-machine ownership transfer
remain DBA operations. Use a different producer UUID and credential for each installation. Never
move an installation by merely giving a second machine the old permanent token.

A clone holding the same bearer credential *and* the winning durable recovery request is the
same security principal; HTTPS/PostgreSQL cannot distinguish its physical machine. Protect
local state/credentials, use one local worker ownership lock and do not clone identities. A
stale instance with only its old session cannot discover or recover the winner's subsequent
session. Explicit transfer to a distinct producer always fails the old producer's stream checks.
If ownership is partially transferred, the old manifest fails; remaining streams still have
their explicit database owner. There is no operation that restores transferred streams.

## Durable client state transitions for milestone 3

1. Preserve pending observations and immutable staged batch bytes through all errors. Keep the
   current session identity, dataset epochs and acknowledged ownership manifest durably local.
2. On normal startup, resolve any outstanding recovery operation first by replaying its saved
   request ID and contents. Otherwise admit/renew the saved session. A live valid session can
   continue without recovery; an expired one may recover using its saved expected identity.
3. Before sending recovery, durably stage one random recovery_id plus the complete request.
   Serialize this with the future worker's local ownership lock. Do not create competing recovery
   IDs after a timeout, sleep or process restart while that operation's result is uncertain.
4. Validate a 200 receipt against producer, recovery ID, previous session/generation and exact
   stream epochs/generations, and require the next generation and committed state. Persist the
   receipt and active-session transition atomically in the local durable state before use. The
   future worker will implement this; HTTP examples below are not durable checkpoint machinery.
5. Check old batch receipts using their original IDs. A committed batch needs no financial replay.
   A missing receipt is not proof an in-flight request could not commit; observation deduplication
   remains necessary. Do not change already staged bytes under their original batch ID.
6. For records still needing upload, stage a new batch ID/envelope using the recovered session,
   retaining exact observation IDs, source positions, dataset epochs and source/collector times.
   Preserve the old batch for reconciliation. An observation committed in another batch is
   deduplicated by the existing ledger; correction and latest-quote ordering remain enforced.
7. Renew the live session periodically (for example every 30 seconds). If a replayed recovery
   receipt's lease has already expired, persist that known result, then stage a *new* recovery
   operation expecting that now-known session. The old request never extends itself. Do not
   automatically follow a recovery_obsolete/ownership/session fence to an unknown replacement.

| Situation | Required client behavior |
|---|---|
| Normal process restart | Load durable session and pending recovery/batches. Replay unresolved recovery first; otherwise admit/renew a still-live session. |
| Short internet interruption or laptop sleep | Keep observations/staged bytes and bounded retry state; reconnect with TLS verification. Renew if still live. |
| Outage longer than the lease | Recover the unchanged authorized producer using the saved expected session and complete manifest. No routine DBA intervention. |
| Lost renewal response | Retry renewal with the same session. If it has expired, stage recovery; do not assume a new identity or change observations. |
| Lost recovery response | Retry the same durable recovery ID/logical body. A committed current result replays; an uncommitted attempt can execute once after rollback. |
| Company server restart during recovery | Same retry rule. Before commit the transaction rolls back; after commit the saved receipt survives. No local records are discarded. |
| Intentional ownership transfer | Stop on ownership/session fence. An administrator assigns a distinct producer/credential and higher ownership generations; the old installation cannot take over. Disable/rotate old credentials if all access should cease. |
| Credential rotation | Obtain the new token privately; SQL key ID and server hash files must be coordinated. Old retained files fail. With the valid new key, retain known session/recovery state and retry the same operation as appropriate. |
| Producer revocation | Stop uploads/recovery on 401/403; retain local pending data and notify the operator. Do not repeatedly invent recovery IDs or auto-enable anything. |
| Configured streams/epoch/generation changed | Fail closed on the saved manifest; review the intended provisioning/configuration. Never guess new epochs, drop streams or reset positions to regain access. |

The full manifest can be refreshed through ordinary admission while the known session is valid.
A deliberate grant change during a prolonged outage may need operator-supplied configuration;
automatic recovery is for unchanged authorization, not automatic permission discovery. Initial
missing durable session state also requires reviewed provisioning; there is no bootstrap/takeover
API. Recovery receipts are retained, with no automatic purge that could undermine idempotency.

## Errors and backoff

Existing sanitized error bodies and Retry-After behavior are retained. New 409 codes are
producer_session_active (renew/admit this known live session), recovery_payload_conflict (do
not alter the saved operation), recovery_ownership_changed, recovery_obsolete and
session_generation_exhausted. Wrong previous identity uses existing producer_session_fenced.
Only 429/503 have retryable=true; keep the request and retry with bounded exponential backoff,
jitter and Retry-After. 401/403 require credential/operator action. Fencing 409 responses require
classification, never generic blind retries or discovery of another session. invalid_recovery
is 422; body size is 413. Internal SQL/connection failures remain sanitized 503; unexpected
invariants remain 500. A malformed/unauthorized request never advances the producer generation.
Operational request-budget consumption is separate and can still occur for a rejected request.

## Windows and Linux HTTP examples

These examples send a **previously durably staged** request file. They preserve that file and
save the response separately for validation; they do not implement a sync worker or atomically
switch local checkpoints. Use the producer's own private token, approved company hostname/CA
and a private output directory. An installed company CA or an explicitly configured trusted CA
bundle is required where appropriate. Tokens stay out of command-line arguments and output.

PowerShell 7, with normal certificate validation and redirects disabled:

```powershell
$recoveryRequest='C:\ProgramData\Marketdata\state\recovery-request.json'
$tokenFile='C:\ProgramData\Marketdata\secrets\ingest_token'
$responseFile='C:\ProgramData\Marketdata\state\recovery-response.json'
$body=[IO.File]::ReadAllBytes($recoveryRequest)
$headers=@{Authorization='Bearer '+[IO.File]::ReadAllText($tokenFile).Trim()}
$response=Invoke-RestMethod -Method Post -Uri 'https://marketdata.company.example/api/ingest/v1/session/recover' -Headers $headers -ContentType 'application/json' -Body $body -MaximumRedirection 0 -TimeoutSec 30
$response | ConvertTo-Json -Depth 20 | Set-Content -LiteralPath $responseFile -Encoding utf8NoBOM
```

Restrict both state and secret directories with Windows ACLs. Catch HTTP/transport failures in
the future worker without logging headers or exception details containing credentials. Validate
all fields above before adopting the response; a response file alone is not a delivery checkpoint.

Linux Bash/curl, using a private temporary header file and no redirect following:

```bash
umask 077
request_file=/var/lib/marketdata/state/recovery-request.json
token_file=/etc/marketdata/secrets/ingest_token
response_file=/var/lib/marketdata/state/recovery-response.json
header_file=$(mktemp)
trap 'rm -f -- "$header_file"' EXIT
printf 'Authorization: Bearer %s\n' "$(cat "$token_file")" > "$header_file"
curl --silent --show-error --fail-with-body --proto '=https' --tlsv1.2 \
  --connect-timeout 10 --max-time 30 --header @"$header_file" \
  --header 'Content-Type: application/json' --data-binary @"$request_file" \
  --output "$response_file" \
  'https://marketdata.company.example/api/ingest/v1/session/recover'
```

Check curl's exit status and validate a successful receipt before adopting it. Error output or
an incomplete response file is not a receipt. Retry from the original saved request file after
uncertain results. Neither example sends observations, changes epochs or edits old staged batches.

## Clock and freshness expectations

Synchronize company PostgreSQL/server and collector machines to trusted time sources. Windows
`w32tm /query /status` and Linux `timedatectl status` are read-only diagnostics where available.
Lease decisions use the database clock; the client can schedule renewal using monotonic time
and server-provided timestamps rather than trusting its wall clock alone. Generations and
ownership, not clock values, are the authority for fencing. Large database-clock steps can
shorten/extend lease duration operationally, so monitor time synchronization.

The existing five-second future source/collector timestamp guard is unchanged. A 422
source_clock_ahead or collector_clock_ahead must retain the original pending observation and
batch identity. Check clocks before retrying. A small ahead observation may become acceptable
when trusted server time catches up; do not clamp/rewrite its genuine timestamps or payload
under the old batch ID. A badly future-dated observation needs explicit quarantine/investigation
and any legitimate source correction as a new immutable observation, not fabricated times or
silently discarded data. Session recovery cannot repair erroneous historical timestamps.

A recovered session, successful upload or healthy API is not proof of fresh data. Quote freshness
uses genuine source/collector times; captured status retains its own expiry and is invalidated
by the session change until valid new captured status arrives. Old queued data remains historical
or stale when appropriate. No candle-close substitute or complete quote-history guarantee is
introduced here.

## Reproduce on isolated databases

```powershell
docker compose -p marketdata-v11-m21-tests -f compose.v11-m21-test.yaml up -d --wait
$env:DATABASE_URL='postgresql://m21_test:disposable_test@127.0.0.1:55965/marketdata_v11_m21_test'
uv run --no-sync alembic upgrade head
$env:TEST_DATABASE_URL=$env:DATABASE_URL
uv run --no-sync pytest -q --junitxml=artifacts/v11-m21-full-pg16.xml
$env:DATABASE_URL='postgresql://m21_test:disposable_test@127.0.0.1:55966/marketdata_v11_m21_test'
uv run --no-sync alembic -x timescale=true upgrade head
$env:TEST_DATABASE_URL=$env:DATABASE_URL
uv run --no-sync pytest -q --junitxml=artifacts/v11-m21-full-timescale.xml
```

Linux uses the same commands with export DATABASE_URL=... and
export TEST_DATABASE_URL="$DATABASE_URL". OpenSSL generates disposable TLS certificates. Missing
OpenSSL causes the TLS tests to skip and must be reported; these runs require it. Test fixtures
clear only their `_test` database and migration cases create/drop uniquely named `_test` DBs in
the task cluster. Process-kill tests terminate only their own test TLS child processes and one
explicit task-DB connection. Never substitute the live collector DSN, reuse a production volume
or run tests concurrently on the same database. Final v1.1 packaging, standard image build,
company deployment and actual WAN/source-worker qualification remain later work.
